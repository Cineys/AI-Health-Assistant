# 健康助手项目系统架构说明

## 1. 项目整体定位

本项目是一个基于微信小程序和 Python FastAPI 后端的健康助手系统。整体能力包括心情打卡、AI 医疗问诊、心理疏导、膳食建议、就诊参考报告、月度/年度健康总结、用药管理和服药打卡。

从源码结构看，系统采用前后端分离架构：

- 前端：微信小程序，负责页面交互、本地缓存、流式 AI 展示和业务入口整合。
- 后端：FastAPI 单体服务，负责登录鉴权、业务接口、AI 对话编排、报告生成、RAG 检索和数据持久化。
- 数据层：MySQL 保存用户业务数据，ChromaDB 保存医学知识向量库。
- 外部服务：微信登录接口、DashScope 通义千问大模型、Huatuo 医学语料。

整体调用链如下：

```text
微信小程序前端
  pages/* 页面层
  utils/* 前端服务封装层
        |
        | HTTP / SSE / Bearer Token
        v
FastAPI 后端服务
  app.py      API 路由、RAG、AI 对话、报告、业务接口
  auth.py     微信登录、JWT 鉴权
  database.py MySQL ORM 模型与数据库连接
        |
        | SQLAlchemy / ChromaDB / DashScope / WeChat API
        v
外部与基础服务
  MySQL
  ChromaDB 本地向量库
  DashScope 通义千问
  微信 jscode2session 登录接口
  Huatuo 医疗 JSONL 语料
```

## 3. 前端架构设计

前端是原生微信小程序结构，由全局入口、页面模块和工具模块三部分组成。

### 3.1 全局入口模块

主要文件：

- `app.js`
- `app.json`
- `app.wxss`

`app.json` 定义小程序页面列表、窗口样式和底部 TabBar。当前 TabBar 包含首页、AI 诊室和我的三个主入口。

`app.js` 是小程序启动入口。在 `onLaunch` 中调用 `wx.login` 获取微信临时 code，然后通过 `utils/api.js` 调用后端 `/api/login`。登录成功后，将后端返回的 JWT token 写入本地缓存，并维护 `globalData` 中的用户状态。

### 3.2 页面功能模块

| 页面目录 | 功能定位 | 主要职责 |
|---|---|---|
| `pages/index` | 首页与心情打卡 | 展示欢迎信息、周历、心情选择、健康功能入口 |
| `pages/chat` | AI 医疗问诊 | 创建会话、发送消息、接收 SSE 流式 AI 回复、生成报告 |
| `pages/emotional` | 心理疏导/膳食管家 | 复用 `/api/chat`，通过不同 mode 进入情绪陪伴或膳食建议 |
| `pages/profile` | 我的与健康统计 | 昵称头像、心情热力图、统计数据、报告和功能入口 |
| `pages/report` | 单份报告展示 | 展示当前生成报告，或按 id 拉取报告详情 |
| `pages/reports` | 报告列表 | 获取历史报告列表并跳转详情 |
| `pages/monthly` | 月度报告 | 调用后端生成或读取月度总结 |
| `pages/annual` | 年度报告 | 调用后端生成或读取年度总结 |
| `pages/medication` | 用药助手 | 药品管理、服药时段、服药打卡 |

### 3.3 前端工具模块

| 文件 | 职责 |
|---|---|
| `utils/config.js` | 前端统一配置：后端 `BASE_URL` 的唯一来源 |
| `utils/api.js` | 统一封装后端 HTTP 请求，从 `utils/config.js` 读取 `BASE_URL`，自动附带 JWT token |
| `utils/mood.js` | 心情打卡本地缓存、日期处理、连续打卡统计 |
| `utils/medication.js` | 用药列表和打卡本地缓存，与后端进行双写同步 |

`utils/api.js` 是普通 REST 接口的统一入口。`BASE_URL` 统一在 `utils/config.js` 中定义，`utils/api.js` 通过 `require('./config')` 读取，不再由各调用方分别维护；请求经 `wx.request` 发起，并在需要鉴权时自动添加 `Authorization: Bearer <token>` 请求头。

需要注意的是，AI 对话接口 `/api/chat` 因为需要 SSE 流式输出，所以没有完全走 `utils/api.js`，而是在 `pages/chat/chat.js` 和 `pages/emotional/emotional.js` 中直接调用 `wx.request`，启用 `enableChunked` 并解析 `text/event-stream` 数据。

## 4. 后端架构设计

后端位于 `backend-server/` 目录，是一个 FastAPI 单体服务。当前业务模块主要集中在 `app.py` 中，基础能力由 `auth.py` 和 `database.py` 拆分提供。

### 4.1 后端核心文件

| 文件或目录 | 职责 |
|---|---|
| `backend-server/app.py` | FastAPI 应用入口、API 路由、AI 对话、RAG、报告、心情、用药等业务逻辑 |
| `backend-server/auth.py` | 微信登录、openid 获取、JWT 生成和解析、当前用户依赖 |
| `backend-server/database.py` | SQLAlchemy 连接配置、ORM 模型、数据库 Session |
| `backend-server/build_vector_db.py` | 从 Huatuo JSONL 构建 ChromaDB 医学向量库 |
| `backend-server/chroma_db_huatuo/` | ChromaDB 持久化数据目录（**本地文件，不包含在公开仓库中**，需用 `build_vector_db.py` 重建） |
| `backend-server/requirements.txt` | Python 后端依赖 |

### 4.2 FastAPI 主服务

`app.py` 承担以下职责：

- 创建 FastAPI 应用。
- 注册 CORS 中间件。
- 启动时初始化 MySQL 数据表。
- 后台预加载 BM25 索引和重排序模型。
- 提供所有 REST API 和 SSE 流式接口。
- 调用 DashScope 通义千问生成对话、报告和总结。
- 连接 ChromaDB 做医学知识检索。

后端主服务启动方式在源码注释中给出：

```bash
uvicorn app:app --host 0.0.0.0 --port 8000 --reload
```

## 5. 后端功能模块划分

### 5.1 登录与用户模块

主要代码：

- `backend-server/auth.py`
- `backend-server/app.py`
- `backend-server/database.py` 中的 `User`

主要接口：

```text
POST  /api/login
PATCH /api/user
```

调用流程：

```text
小程序启动
  -> wx.login 获取 code
  -> POST /api/login
  -> 后端调用微信 jscode2session
  -> 获取 openid
  -> 查询或创建 User
  -> 生成 JWT token
  -> 前端保存 token
```

后续需要登录的接口都通过 `get_current_user` 依赖解析当前用户。

### 5.2 AI 对话模块

主要代码：

- `pages/chat/chat.js`
- `pages/emotional/emotional.js`
- `backend-server/app.py`

主要接口：

```text
POST /api/chat
```

该接口使用 SSE 流式响应。前端收到分块数据后解析 `data:` 字段，并实时追加到 AI 消息气泡。

后端根据请求中的 `mode` 分为三类：

- `medical`：医疗问诊模式。
- `emotional`：心理疏导模式。
- `diet`：膳食管家模式。

医疗问诊模式会进一步调用意图分类器，分为：

- `chat`：普通闲聊。
- `medical`：正常医疗问诊。
- `emergency`：紧急风险场景。

医疗问诊的完整链路：

```text
用户输入
  -> /api/chat
  -> classify_intent 调用 Qwen 做意图分类
  -> medical 分支进入 RAG
  -> hybrid_retrieve_context 检索医学知识
  -> build_system_prompt 拼接系统提示词
  -> stream_qwen 调用 DashScope 流式生成
  -> StreamingResponse 返回 SSE
```

### 5.3 RAG 医学知识检索模块

主要代码：

- `backend-server/app.py`
- `backend-server/build_vector_db.py`
- `backend-server/chroma_db_huatuo/`
- `huatuo_sample.jsonl`

RAG 模块采用混合检索设计：

```text
Query
  ├── ChromaDB 向量语义检索
  └── BM25 关键词检索
        |
        v
RRF 融合与去重
        |
        v
CrossEncoder 重排序
        |
        v
Top-K 医学参考资料
        |
        v
注入医疗问诊 Prompt
```

其中：

- ChromaDB 用于语义相似度召回。
- BM25 用于关键词召回。
- RRF 用于融合不同召回路径。
- CrossEncoder 用于对候选文档重排序。
- DashScope Qwen 根据检索上下文生成自然语言回复。

向量库由 `build_vector_db.py` 构建，它读取 Huatuo JSONL 数据，转换为统一的“问题 + 回答”文本，再写入 ChromaDB。

### 5.4 报告模块

主要代码：

- `pages/chat/chat.js`
- `pages/report/report.js`
- `pages/reports/reports.js`
- `pages/monthly/monthly.js`
- `pages/annual/annual.js`
- `backend-server/app.py`
- `database.py` 中的 `Report`

主要接口：

```text
POST /api/report
GET  /api/reports
GET  /api/report/{report_id}
GET  /api/reports/monthly
GET  /api/reports/annual
```

标准问诊报告生成流程：

```text
用户完成问诊
  -> 前端提交完整 messages
  -> POST /api/report
  -> 后端读取近 7 天心情记录
  -> 拼接报告生成 Prompt
  -> 调用 DashScope 生成 JSON 报告
  -> 保存到 Report 表
  -> 前端展示报告
```

月度和年度报告则基于历史心情数据、历史问诊报告和统计信息进行聚合，再调用大模型生成总结。

### 5.5 心情打卡模块

主要代码：

- `pages/index/index.js`
- `pages/profile/profile.js`
- `utils/mood.js`
- `backend-server/app.py`
- `database.py` 中的 `MoodRecord`

主要接口：

```text
POST /api/mood
GET  /api/mood/recent
GET  /api/mood/stats
```

该模块采用本地优先设计：

```text
用户打卡
  -> 先写入本地 wx storage
  -> 页面立即刷新
  -> 如果有 token，则同步 POST /api/mood
```

个人页加载时：

```text
profile 页面打开
  -> 先读取本地 mood_records 构建热力图
  -> 如果有 token，则请求 /api/mood/recent
  -> 合并远端数据到本地缓存
  -> 请求 /api/mood/stats 获取统计数据
```

这种设计保证了即使用户未登录或网络不可用，心情打卡仍能正常使用。

### 5.6 用药助手模块

主要代码：

- `pages/medication/medication.js`
- `utils/medication.js`
- `backend-server/app.py`
- `database.py` 中的 `Medication` 和 `MedicationCheckin`

主要接口：

```text
GET    /api/medications
POST   /api/medications
PATCH  /api/medications/{med_id}
DELETE /api/medications/{med_id}
POST   /api/medications/checkin
GET    /api/medications/checkin
```

用药模块同样采用本地缓存和后端同步结合的设计：

```text
读取
  -> 先读取本地 med_list / med_checkin
  -> 登录后从后端同步覆盖缓存

写入
  -> 未登录：只写本地缓存
  -> 已登录：调用后端 API，成功后更新本地缓存

服药打卡
  -> 本地乐观更新
  -> 后台静默同步后端
```

## 6. 数据模型设计

数据模型集中定义在 `backend-server/database.py`。

核心实体关系：

```text
User
  1 - N MoodRecord
  1 - N ChatSession
  1 - N Report
  1 - N Medication
  1 - N MedicationCheckin

ChatSession
  1 - N ChatMessage
  1 - N Report

Medication
  1 - N MedicationCheckin
```

主要模型说明：

| 模型 | 表名 | 职责 |
|---|---|---|
| `User` | `users` | 微信用户主体，保存 openid、昵称 |
| `MoodRecord` | `mood_records` | 每日心情、emoji、标签、日记 |
| `ChatSession` | `chat_sessions` | 一次对话会话，区分 medical、emotional、diet |
| `ChatMessage` | `chat_messages` | 会话消息，保存用户和 AI 的对话内容 |
| `Report` | `reports` | 标准报告、月度报告、年度报告 |
| `Medication` | `medications` | 用户药品记录 |
| `MedicationCheckin` | `medication_checkins` | 某天某药某时段的服药打卡 |

MySQL 连接通过 `.env` 中的 `DATABASE_URL` 提供。后端启动时会调用 `init_db()` 创建表结构。

## 9. 架构模式总结

### 9.1 前后端分离

小程序只负责页面、交互、本地缓存和 API 调用。后端负责业务规则、AI 编排、数据保存和外部服务集成。

### 9.2 单体后端

后端目前是单体结构，所有业务 API 主要集中在 `app.py`。虽然没有拆分 router 和 service 层，但源码中已经通过注释块按业务划分出登录、心情、会话、报告、用药、RAG 等模块。

### 9.3 AI 编排层

`app.py` 不只是普通业务接口层，还承担 AI Gateway 的角色。它负责：

- 判断对话模式。
- 调用意图分类器。
- 选择是否进入 RAG。
- 拼接 Prompt。
- 调用大模型。
- 将模型输出流式返回前端。

### 9.4 RAG 增强问诊

医疗问诊不是直接调用大模型，而是先从 Huatuo 医学知识库中检索相关资料，再将参考资料注入系统 Prompt。这种设计可以提高医学回答的相关性和一致性。

### 9.5 本地优先与离线降级

心情和用药模块都支持未登录或网络异常时继续使用。本地缓存是第一层数据源，后端同步是增强能力。

### 9.6 业务数据与知识数据分离

MySQL 保存用户业务数据，ChromaDB 保存医学知识数据。两类数据分别服务不同场景：

- MySQL 服务用户画像、记录、报告、用药等业务流程。
- ChromaDB 服务医疗问诊时的知识检索。

## 10. 后续架构演进建议

如果项目继续扩展，可以考虑以下方向：

1. 将 `app.py` 拆分为多个 FastAPI router，例如 `chat_router`、`report_router`、`mood_router`、`medication_router`、`user_router`。
2. 增加 service 层，将 AI 调用、报告生成、RAG 检索、统计聚合从路由函数中拆出。
3. （已完成）前端 `BASE_URL` 已提取到统一配置 `utils/config.js`，`utils/api.js` 与 `pages/chat/chat.js`、`pages/emotional/emotional.js` 均从该文件读取，不再多处维护。
4. 对 SSE 解析逻辑做前端复用封装，减少 `chat` 和 `emotional` 页面的重复代码。
5. 将本地缓存和云端同步策略抽象为统一的数据同步层。
6. 为报告生成、RAG 检索、用药打卡等关键路径增加自动化测试。
